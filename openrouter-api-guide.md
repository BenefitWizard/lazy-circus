# Руководство по работе с OpenRouter API

OpenRouter предоставляет единый унифицированный интерфейс для взаимодействия с множеством языковых моделей (LLM) от различных провайдеров. Схемы запросов и ответов максимально приближены к стандарту **OpenAI Chat API**, что делает интеграцию с существующим кодом крайне простой.

## Совместимость с клиентами OpenAI (OpenAI SDK)

OpenRouter спроектирован так, чтобы быть **полностью совместимым (drop-in replacement)** с официальными SDK OpenAI (для Python, Node.js и других языков), а также инструментами вроде LangChain и LlamaIndex.

Для использования OpenRouter через стандартный клиент OpenAI, достаточно изменить `baseURL` и передать API ключ OpenRouter, а также (опционально) добавить специфичные заголовки для идентификации вашего приложения.

**Пример на Node.js:**
```javascript
import OpenAI from 'openai';

const openai = new OpenAI({
  baseURL: 'https://openrouter.ai/api/v1',
  apiKey: process.env.OPENROUTER_API_KEY,
  defaultHeaders: {
    'HTTP-Referer': 'https://yoursite.com', // Опционально: для отображения и рейтинга на openrouter.ai
    'X-OpenRouter-Title': 'Your App Name',  // Опционально: имя вашего приложения
  }
});

const completion = await openai.chat.completions.create({
  model: 'anthropic/claude-3.5-sonnet', // Модели указываются с префиксом провайдера (например, openai/, anthropic/, google/)
  messages: [{ role: 'user', content: 'Привет! Как дела?' }],
});
```

## Основные сценарии работы

### 1. Базовая генерация текста и мультимодальность
Запросы отправляются методом `POST` на эндпоинт `/api/v1/chat/completions`. Массив `messages` поддерживает роли `user`, `assistant`, `system` и `tool`. Для мультимодальных моделей в `content` можно передавать массив с текстом и изображениями (`image_url`).

### 2. Структурированный вывод (Structured Outputs)
Для получения строго форматированных ответов используйте параметр `response_format`. OpenRouter поддерживает два режима (для моделей, которые это умеют):
* `{ type: 'json_object' }` — базовый режим, гарантирующий, что ответ будет валидным JSON.
* `{ type: 'json_schema', json_schema: { name: "...", schema: { ... } } }` — строгий режим, где ответ будет соответствовать переданной JSON-схеме.

### 3. Tool Calling (Вызов функций)
Передача массива `tools` работает точно так же, как в OpenAI. Если провайдер не поддерживает нативный вызов функций, OpenRouter автоматически трансформирует описание ваших функций в YAML-шаблон внутри промпта, позволяя "научить" вызову функций даже те модели, где этого изначально нет.

### 4. Плагины OpenRouter
Уникальная особенность OpenRouter — встроенные расширения возможностей. Передайте массив `plugins` в запросе:
```json
{
  "plugins": [
    { "id": "web" },                 // Поиск в интернете в реальном времени
    { "id": "response-healing" },    // Автоисправление битого JSON в ответе
    { "id": "file-parser" },         // Обработка PDF
    { "id": "context-compression" }  // Middle-out сжатие контекста при переполнении
  ]
}
```

### 5. Assistant Prefill (Предзаполнение ответа)
Вы можете "направить" логику модели, передав в конце массива `messages` сообщение с ролью `assistant` и частичным текстом. Модель продолжит генерацию ровно с этого места (например: `{ role: "assistant", content: "Вот решение шаг за шагом:\n1." }`).

### 6. Умная маршрутизация (Routing)
* **Параметр `models`:** Можно передать массив моделей (например, `models: ["anthropic/claude-3-opus", "openai/gpt-4o"]`). OpenRouter выберет лучшую/дешевую доступную модель.
* **Параметр `route: 'fallback'`:** Позволяет автоматически переключиться на резервного провайдера или графические процессоры, если основной ответил ошибкой 5xx или у вас сработал Rate Limit.
* **Параметр `provider`:** Можно настроить приоритеты провайдеров, например, чтобы не запросы не уходили к провайдерам, требующим хранения данных.

## Подводные камни и важные нюансы (Gotchas)

При переходе на OpenRouter необходимо учитывать несколько специфичных моментов:

### 1. Обработка `finish_reason`
Разные провайдеры по-разному называют причины остановки генерации. OpenRouter всегда **нормализует** поле `finish_reason` к одному из стандартов (`stop`, `length`, `content_filter`, `tool_calls`, `error`). 
* **Нюанс:** Оригинальную причину остановки от конкретного провайдера можно найти в специальном поле `native_finish_reason`.

### 2. Специфичные параметры моделей
Если вы отправляете параметр, который поддерживается одной моделью, но не поддерживается другой (например, параметр `top_k` отправляется в модель от OpenAI, или `logit_bias` для не-OpenAI модели), OpenRouter **просто проигнорирует этот параметр** и выполнит запрос, а не выбросит ошибку 400.

### 3. Работа со статистикой использования в стриминге (`stream: true`)
В отличие от обычного ответа, в режиме потоковой передачи статистики о токенах нет в каждом блоке (chunk).
* **Нюанс:** Объект `usage` со статистикой токенов возвращается **ровно один раз в самом последнем чанке**, перед финальным сообщением `[DONE]`. При этом массив `choices` в этом чанке будет пустым.

### 4. "Мусор" в SSE стриминге
Протокол Server-Sent Events (SSE) в OpenRouter периодически отправляет payload-комментарии (пустые события) для поддержания активности соединения. Ваш код или парсер должен быть готов игнорировать неизвестные события, чтобы не упасть с ошибкой парсинга JSON.

### 5. Получение точной стоимости и логов
Подсчет токенов ведется с использованием нативных токенизаторов каждой модели.
Если вам нужно узнать точную стоимость (`cost`) завершенного запроса (особенно после стриминга, когда стоимость может не посчитаться мгновенно), вы можете использовать API получения статистики.
* **Решение:** Сохраните идентификатор генерации (`id`) из ответа API и выполните GET-запрос на `/api/v1/generation?id=$GENERATION_ID`. Там будет лежать детальная информация о токенах, цене и провайдере.

### 6. Отсутствие параметра `model`
Если в запросе не передать параметр `model`, OpenRouter не упадет с ошибкой, а попытается использовать модель по умолчанию, установленную в настройках аккаунта пользователя (или плательщика). Чтобы избежать сюрпризов, всегда явно задавайте модель.

## Совместимость с клиентом на Haskell (MercuryTechnologies/openai)

Если вы используете Haskell-клиент [MercuryTechnologies/openai](https://github.com/MercuryTechnologies/openai) для работы с OpenRouter, учтите, что **не все функции OpenRouter будут доступны из коробки**. Это связано с тем, что данный клиент строго типизирован и использует жестко заданную структуру данных `CreateChatCompletion` для сериализации запросов.

### Ограничения (недоступные функции OpenRouter)
Поскольку в типах `CreateChatCompletion` нет универсального поля для "extra"-данных или специфичных для OpenRouter параметров, следующие возможности **нельзя** использовать напрямую:
* ❌ **Плагины OpenRouter:** Нет поля `plugins`, поэтому нельзя отправить массив `[{ "id": "web" }]` или `[{ "id": "response-healing" }]`.
* ❌ **Провайдерская маршрутизация:** Нет поля `provider` для настройки предпочтений провайдеров.
* ❌ **Fallback и роутинг:** Нет полей `models` (для массива fallback-моделей) или `route`.

### Поддержка рассуждающих моделей (Reasoning models: o1, o3-mini, DeepSeek-R1)
* ✅ **Полная поддержка!** Клиент MercuryTechnologies/openai недавно обновился для поддержки спецификаций рассуждающих моделей (Reasoning models), которые ввел OpenAI.
* Вы можете передавать параметр `reasoning_effort` (со значениями `ReasoningEffort_Low`, `ReasoningEffort_Medium`, `ReasoningEffort_High`) в запросе. 
* Кроме того, статистика использования (`Usage`) поддерживает чтение поля `reasoning_tokens` (оно успешно парсится в `usage.completion_tokens_details.reasoning_tokens`), что означает, что вы корректно получите от OpenRouter количество токенов, потраченных на логику/рассуждения модели.

### Передача PDF
* ❌ **Нативный парсинг недоступен:** OpenRouter реализует парсинг PDF через плагин `file-parser`. Так как массив `plugins` нельзя передать в запросе (как описано выше), нативная обработка PDF будет недоступна.
* ❌ **Мультимодальный Document URL:** Тип `Content` в Haskell-клиенте ограничен тремя вариантами: `Text`, `Image_URL` и `Input_Audio`. Вы не сможете передать специфичный тип `{ "type": "document_url" }`.
* 💡 **Рабочий костыль:** Если модель поддерживает извлечение текста по ссылке из обычного текста, вы можете просто передать URL на PDF-файл в виде обычного текста (`Content.Text`). Но нативная интеграция OpenRouter для парсинга документов не сработает из-за отсутствия поля `plugins`.

### Работа с Tools (Tool Calling / Вызов функций)
* ✅ **Полная поддержка!** Клиент имеет встроенные поля `tools`, `tool_choice` и `parallel_tool_calls` в типе `CreateChatCompletion`.
* **Магия OpenRouter:** Когда вы передаете JSON-схему функции (через типы `Aeson`) в поле `tools` через этот клиент, OpenRouter сделает всю "грязную работу":
  * Если модель (например, OpenAI или Anthropic) поддерживает нативный вызов функций, OpenRouter просто проксирует этот запрос.
  * Если модель **не** поддерживает нативные функции (например, многие open-source модели), OpenRouter **автоматически** преобразует ваш массив `tools` в специальный YAML-шаблон, вшивает его в системный промпт, а затем парсит ответ модели, возвращая вам стандартный `tool_calls` в ответе!
* Для вас в Haskell-коде это означает, что код вызова функций будет работать одинаково хорошо как для GPT-4o, так и для Llama-3 или Mistral.

### Структурированный вывод (Structured Outputs / JSON Schema)
* ✅ **Полная поддержка!** В клиенте присутствует поле `response_format :: Maybe ResponseFormat`.
* OpenRouter полностью поддерживает стандарты OpenAI:
  * **JSON Mode:** Вы можете передать формат `{ "type": "json_object" }`, чтобы заставить модель вернуть валидный JSON.
  * **Strict JSON Schema:** Вы можете передать строгую схему через формат `json_schema` (с флагом `strict: true`). В Haskell-клиенте вы формируете схему через `Aeson.object` (как показано в примерах README библиотеки).
* OpenRouter также применяет свои внутренние оптимизации: если модель нативно не поддерживает строгий вывод по JSON-схеме, OpenRouter может использовать техники грамматического ограничения (constrained decoding) или промптинга на своей стороне, чтобы гарантировать, что ответ, который придет в ваш Haskell-клиент, будет строго соответствовать переданной схеме.
